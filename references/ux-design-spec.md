## 0. 使用说明

### 0.1 三条主线

| 层 | 回答什么问题 | 来源 | 在本文的位置 |
| --- | --- | --- | --- |
| 可用性层 | 这个流程**能不能用、好不好用** | 尼尔森十大原则 | 第 1–11 章 |
| 视觉执行层 | 界面**看起来对不对**，错在哪、改成什么值 | Refactoring UI | 第 12 章 |
| 场景落地层 | 具体到表单 / 空态 / 报错 / 帮助 / 页面瘦身**怎么改** | 五讲卡片 | 各章「落地规范」 |

### 0.2 严重度与处置

| 级别 | 判据 | 处置 |
| --- | --- | --- |
| **P0** | 关键任务无法完成、键盘操作被阻断、核心控件无法被辅助技术识别、发生严重数据丢失，或关键文本对比度不达标 | 阻断发布 |
| **P1** | 偏离系统值（间距/字号/颜色/阴影）、组间距歧义、操作层级未分级 | 当次迭代修复 |
| **P2** | 缺打磨、层级未用足、组件默认态 | 排期优化 |

### 0.3 优先级冲突时

**安全与无障碍底线 > 任务可用性 > 一致性 > 视觉美观。** 冲突时优先保护安全、可访问性和任务完成能力，并在评审记录中说明。

## 2. H1 · 系统状态的可见性

> 系统应始终在合理时间内，通过恰当反馈让用户了解正在发生什么。

### 2.1 落地规范

1. **空态必须说明原因**（C2-1）。新建为空与搜索为空是两种状态，不得统一写「暂无数据」。

| 空态类型 | 必须说清 | 必须提供 |
| --- | --- | --- |
| 新建 / 首次进入 | 还没有什么，以后会有什么 | 创建主按钮 |
| 搜索无结果 | 回显关键词，说明未匹配 | 清除搜索 |
| 筛选无结果 | 说明由条件导致 | 重置筛选 |
| 异常 / 无权限 | 原因 + 解决路径 | 重试 / 联系客服 |

2. **反馈就地出现**（C4-2）。错误贴在出错的那一处并框出来，不要「屏幕中间闪两秒」。
3. **进度可见**。耗时 > 1s 的操作给加载态；> 10s 给进度或可中断提示（响应时间三档依据见 T17）。
4. **阴影表达层级而非重要性**（§6.2）。静态卡片用最浅一档，浮层、弹窗才逐级加深——用户靠阴影判断“这一层在上面”。

### 2.2 正反例

| 场景 | ❌ 不达标 | ✅ 规范 |
| --- | --- | --- |
| 列表为空 | 「暂无数据」 | 「还没有收藏 · 看到喜欢的点收藏，就会出现在这」+ 去逛逛 |
| 搜索无果 | 「暂无数据」 | 「没搜到『邀请家人』」+ 清除搜索 |
| 保存失败 | 屏幕中间 toast 闪 2 秒 | 表单顶部常驻条 + 出错字段红框 + 就地说明 |

### 2.3 自查项

- [ ] 每类空态是否写清了“为什么空”？
- [ ] 需要用户修正的错误是否就地保持可见，普通成功反馈是否避免不必要地打断任务？
- [ ] 长耗时操作是否有加载/进度反馈？

## 3. H2 · 系统与真实世界的匹配

> 系统应使用用户熟悉的词、概念和顺序，而不是系统导向的术语。

### 3.1 落地规范

1. **用用户的原话做标题**（C3-2）。功能名写「邀请家人」，不写「成员权限配置」。
2. **搜索要覆盖用户真实的表达方式**。根据任务风险、数据规模和搜索日志选择组合策略，不预设单一技术架构：
   - **词法召回**：支持合理的分词、部分匹配、拼写容错；「邀请家」等输入可以命中「邀请家人」。
   - **语义召回**：当用户常用同义表达、口语提问或意图描述无法由词法召回覆盖时，引入语义检索或经过维护的同义词规则。「拉人进群」「怎么加人」应能找到「邀请家人」相关帮助。
   - **混合与排序**：词法、语义、权限和业务相关性共同决定结果；用真实查询集测量召回率、零结果率和首条结果成功率。
   - **降级策略**：语义服务不可用时回退到可用的词法检索并记录降级；是否维护同义词表由语言、领域与维护成本决定。
3. **合并标签与值**（§2.5.2）。“库存 12 件”优于“库存：12”；“3 间卧室”优于“卧室：3”。
4. **顺序跟现实一致**。地址由大到小、时间由近及远；不要按数据库字段顺序排。
5. **量词与单位本地化**。金额带币种，日期用「昨天 / 3 天前」优先于绝对时间戳。

### 3.2 正反例

| 场景 | ❌ 不达标 | ✅ 规范 |
| --- | --- | --- |
| 帮助标题 | 成员权限配置说明 | 邀请家人 |
| 帮助搜索 | 仅标题精确匹配，搜「拉人进群」0 条结果 | 模糊 + 语义搜索，口语叫法均命中「邀请家人」 |
| 规格展示 | 屏幕尺寸：6.1 英寸 | 6.1 英寸屏幕 |
| 时间 | 2026-10-28 14:32:11 | 3 分钟前 |

### 3.3 自查项

- [ ] 界面文案中是否出现内部术语、字段名、英文缩写？
- [ ] 错别字、部分词、口语说法搜索是否都能命中（模糊 + 语义）？
- [ ] 用户最常用的 3 种叫法，是否都能搜到？
- [ ] 信息顺序是否与用户现实中的认知顺序一致？

## 4. H3 · 用户的控制权和自由

> 用户常会误操作，需要一个明确标注的“紧急出口”。

### 4.1 落地规范

1. **失败不清空**（C4 收尾）。提交失败时保留可安全复用的已填内容，只标出出错的项目；对已过期的一次性验证码、支付凭据等敏感字段，明确提示是否需要重新输入。
2. **可撤销**。按操作风险选择撤销、二次确认或延迟执行；可逆操作优先提供撤销，影响重大或不可恢复的操作必须明确后果并确认。
3. **危险操作降级**（§2.8.1）。破坏性按钮不做主操作样式；确认弹窗内它才是主操作。
4. **随时可退出**。弹窗、流程页支持返回/关闭，未保存时给出明确选择（存草稿 / 放弃 / 继续编辑）。
5. **空态的一键复位**。搜索/筛选无结果时提供“清除条件”，而不是让用户手动逐个删。

### 4.2 自查项

- [ ] 提交失败后，可安全复用的已填数据是否保留，敏感且已失效的凭据是否明确提示？
- [ ] 是否按风险为破坏性操作提供撤销、二次确认或延迟执行？
- [ ] 多步流程中途退出，是否有草稿或明确的放弃确认？

## 5. H4 · 一致性和标准

> 用户不应猜测不同的话、情况或操作是否意味着同一件事。

### 5.1 落地规范

1. **所有值来自系统**，禁止手调一次性数值（§1.5.3）：

| 维度 | 系统值 | 规则 |
| --- | --- | --- |
| 间距 | 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96 / 128… | §3.2.2，相邻两档差距 ≥ 25% |
| 字号 | 12 / 14 / 16 / 18 / 20 / 24 / 30 / 36 / 48 / 60 / 72 | §4.1.1d |
| 字重 | 400/500 常规，600/700 强调，**UI 文字不低于 400** | §2.2.b |
| 文字色 | 深 / 中灰 / 浅灰，**最多 3 种** | §2.2.a |
| 阴影 | 5 档高度：`0 1px 3px` / `0 4px 6px` / `0 5px 15px` / `0 10px 24px` / `0 15px 35px` | §6.2.1 |
| 圆角 | 全局统一一档（中性小圆角 / 活泼大圆角，不混用） | §1.4.3 |

2. **同类组件同款**。所有空态、所有报错、所有帮助卡使用同一套结构与文案句式。
3. **同位置同行为**。主操作永远在右下，返回永远在左上；不因页面不同而变。
4. **一词一义**。同一个动作全局只用一个动词（“删除”不混用“移除/清除/销毁”）。

### 5.2 自查项

- [ ] 页面中是否存在不在系统值内的间距、字号、色值？
- [ ] 同类组件（按钮/卡片/空态）在不同页面是否结构一致？
- [ ] 同一动作是否只有一种叫法？

## 6. H5 · 错误预防

> 比好的错误提示更好的，是根本不出现错误。

### 6.1 落地规范（C1 泰斯勒定律）

> 复杂性守恒：**系统承担的越多，用户承担的就越少。**

#### 6.1.1 自动识别 —— 用户手里现成的，能认出来吗？

| 项 | 内容 |
| --- | --- |
| ❌ 不达标 | 让他一段段抄 |
| ✅ 规范 | **整段粘进来，系统拆开填好** |
| 落地 | 提供整段粘贴入口；解析结果按字段回填；未识别字段**高亮待确认**，不静默丢弃；解析失败保留原文并说明哪几项没识别出 |

#### 6.1.2 智能默认 —— 这一栏，能给个靠谱的默认吗？

| 项 | 内容 |
| --- | --- |
| ❌ 不达标 | 每次从空白开始选 |
| ✅ 规范 | **先选好最可能的，错了一点就改** |
| 落地 | 默认值优先级：当前上下文 > 历史行为 > 设备/位置 > 全局高频；默认值必须**可见**（预选中，不是占位符）；无依据不猜（默认值效应依据见 T11） |

#### 6.1.3 自动补全 —— 要打字的栏，能边打边补全吗？

| 项 | 内容 |
| --- | --- |
| ❌ 不达标 | 让他一个字一个字打全 |
| ✅ 规范 | **打几个字，给出整条建议** |
| 落地 | 1–2 字符触发；建议带来源（历史/热门）；键盘可上下选择、回车确认；离线降级为本地历史 |

#### 6.1.4 约束优于校验

- 能选就不要填（日期选择器、枚举、步进器）。
- 格式约束前置：手机号分段、金额千分位、长度上限即时提示。
- 破坏性操作前置确认，确认文案写清后果（“删除后 30 天内可恢复”）。

### 6.2 验收口径

> 替他填了，他能**一眼核、一下改**吗？只有他知道的，留给他。

### 6.3 自查项

- [ ] 成段信息（地址/发票/证件）是否支持整段粘贴自动拆分？
- [ ] 有依据的枚举字段是否预选最可能值？
- [ ] 打字类输入是否有补全建议？
- [ ] 所有默认值是否可见、可核对、可单字段修改？

## 7. H6 · 识别而非回忆

> 尽量减少用户记忆负担：把选项摆出来，而不是让用户记住后输入。

### 7.1 落地规范

1. **历史信息自动带出**。上次地址、上次发票抬头、最近联系人，直接列出供选。
2. **帮助就地出现**（C3-1）。卡住的位置加一行提示，点开原地展开卡片，不要跳转到 40 篇的帮助中心。
3. **选项可见**。不要求用户记住编码、路径、命令；下拉带图标与说明。
4. **上下文常量外置**。当前步骤、已选条件、剩余步骤数始终可见。

### 7.2 自查项

- [ ] 用户是否必须记住上一页的信息才能完成本页？
- [ ] 关键帮助是否需要跳出当前页面才能看到？
- [ ] 可选项是否以列表/建议形式呈现，而非纯输入框？

## 8. H7 · 使用的灵活性和效率

> 对新手隐藏的加速器，对熟手是提效杠杆。

### 8.1 落地规范

1. **熟手通路**。支持键盘快捷键、最近使用、批量操作、模板复用（§8.6：不要被组件的默认形态束缚，下拉可以分组、多列、带说明）。
2. **新手通路**。默认值 + 引导文案 + 示例，让首次使用不依赖教程。
3. **少一步就是效率**。每一个“确认弹窗”“二次跳转”都要问：能否合并？
4. **高频问题转界面**（C3 终极一问）：

> **再问一句：能不能改界面，让他不用问？**

| ❌ | ✅ |
| --- | --- |
| 人人都来问 | 把「邀请家人」摆进账本成员 |

同一问题月咨询量进入 Top 10，或单一入口周咨询 > 50 次，应进入「改界面」需求池，而不是继续写文档。

### 8.2 自查项

- [ ] 高频任务完成路径是否已压到最少步数？
- [ ] 是否提供最近使用/模板/批量等加速手段？
- [ ] Top 咨询问题是否已评估能否用界面消除？

## 9. H8 · 美学和极简设计

> 界面不应包含无关或几乎不需要的信息。

### 9.1 落地规范（C5 四步法）

| 步骤 | 做法 |
| --- | --- |
| ① 写下这页的**那一件事** | 例：结算页 → 下单 |
| ② 每样问：**这一步用得上吗？** | 逐元素过一遍，不留“也许有用” |
| ③ 用不上 → **拿掉，或往后放** | 删除优先，降级次之 |
| ④ 用得上 → **越重要，越大越靠前** | 用尺寸、字重、位置表达优先级 |

### 9.2 层级执行手段

- **不是只靠字号**（§2.2）：字重两档 + 文字色三档就能撑起几乎全部层级。
- **主操作只有一个**（§2.8）：主操作实心、次操作描边、三级操作做成链接。
- **弱化竞争者而非强化主角**（§2.4）：主元素不够突出时，先给周围降噪。
- **减少边框**（§8.5）：优先用背景色差、阴影、留白分隔；已有色差就不要再加边框。
- **省掉多余标签**（§2.5）：格式能自证的信息（邮箱、电话、价格）不加标签。

### 9.3 自查项

- [ ] 这页的“那一件事”能否一句话说清？
- [ ] 页面上是否还有用不上的元素没被拿掉？
- [ ] 主操作是否唯一，且视觉上明显强于次操作？
- [ ] 边框数量是否可以再减一层？

## 10. H9 · 识别、诊断并从错误中恢复

> 错误提示应使用平实语言，精确指出问题，并建设性给出解法。

### 10.1 落地规范（C4 三条）

#### 10.1.1 用户看得懂吗？

| ❌ | ✅ |
| --- | --- |
| 发布失败（4012） | 说出是哪件事：第 3 张图太大了 |

写清**发生了什么 + 在哪 + 为什么**；错误码可以保留，但必须放在人话之后，不单独出现。

#### 10.1.2 知道错在哪吗？

| ❌ | ✅ |
| --- | --- |
| 屏幕中间闪两秒 | 贴在出错的那一处，框出来 |

错误定位到具体字段/区块，就地标注并保持可见，直到用户修正。

#### 10.1.3 知道下一步点哪吗？

| ❌ | ✅ |
| --- | --- |
| 只说失败 | 给个按钮：压缩这张，再发布 |

每条错误必须带**一个可执行动作**（重试 / 修改 / 压缩 / 联系客服），而不是只描述失败。

### 10.2 错误文案模板

```
[发生了什么] + [在哪一项] + [为什么] + [怎么改]
例：第 3 张图太大（超过 10MB），压缩后可继续发布 → [压缩这张] [换一张]
```

### 10.3 自查项

- [ ] 报错是否包含“哪件事、错在哪、下一步”三要素？
- [ ] 错误信息是否常驻到用户修正为止？
- [ ] 每条错误是否至少有一个可点击的解法入口？

## 11. H10 · 帮助和文档

> 理想情况下系统无需帮助；必要时，帮助应易于查找、聚焦用户任务、列出具体步骤。

### 11.1 落地规范（C3 三条）

#### 11.1.1 卡住的地方，看得到帮助吗？

| ❌ | ✅ |
| --- | --- |
| 右上角问号，跳进 40 篇的帮助中心 | 卡住的那块加一行，点开原地出卡片 |

帮助入口就近埋点（字段旁、按钮旁、报错处），形式为内联展开或气泡卡，不打断当前任务。

#### 11.1.2 用他自己的话，搜得到吗？

| ❌ | ✅ |
| --- | --- |
| 搜「邀请家人」，0 条结果 | 标题用用户的话 + 模糊/语义搜索，常说的叫法都指过来 |

- 标题写用户口语；根据真实查询验证词法、语义或混合检索能覆盖常见叫法，不依赖逐字匹配；同义词维护策略按领域和维护成本决定。
- 零结果页必须给最接近的推荐条目，不留死路。

#### 11.1.3 答案能照着点吗？

| ❌ | ✅ |
| --- | --- |
| 一大段，详见 3.2 节 | 3 步，每步一行，带我去 |

步骤 ≤ 3 步，每步一行、动词开头，步骤内提供直达入口；禁止交叉引用章节号。

- [ ] 帮助入口是否在卡点处，而非全局？
- [ ] 帮助标题是否使用用户口语，且搜索支持模糊与语义匹配？
- [ ] 操作类答案是否可拆为 ≤3 步且每步可点？

## 12. 视觉执行基线（Refactoring UI 七视角）

> 走查顺序固定且不可调换：**层级 → 间距 → 排版 → 色彩 → 深度 → 图像 → 收尾**。
> 顺序是因果的：层级没理顺，间距问题的判断会跟着变；间距一改，“要不要加边框”往往自己就没了。

### 12.1 层级（Hierarchy）

- 用层级表达重要性，而不是靠装饰（§2.1）。
- 主元素不突出 → 先削弱竞争元素（§2.4）。
- 标签是最后手段；能合并就合并（§2.5）。
- 语义标签与视觉层级分离：`h1` 是文档结构，不是字号决定（§2.6）。
- 操作分三级：1 主 + 若干次 + 若干链接（§2.8）。

### 12.2 间距与布局（Layout & Spacing）

- **从“白太多”开始，再往下减**（§3.1）。
- **组周围间距必须大于组内间距**（§3.6）——这一条解决大部分“看起来乱”的问题。
- 间距只从系统值取（§3.2）；相邻两档差距 ≥ 25%。
- 内容区不必填满屏幕，600px 就保持 600px（§3.3）。
- 大元素缩小要快于小元素，不要用 em 传递相对尺寸（§3.5）。

### 12.3 排版（Typography）

- 字号只用那 11 档（§4.1.1d）。
- **行宽以 45–75 个拉丁字符作为桌面长文本的参考范围（约 20–35em）**（§4.3）；中文阅读体验应结合实际字体、字号与视口验证。
- 行高随行宽增加而增大（1.5 → 2），随字号增大而减小（大标题可到 1）（§4.5）。
- 长文本左对齐，不居中（§4.7.1）。
- 链接不必都上色，密集场景用字重或悬停下划线（§4.6）。

### 12.4 色彩（Color）

- 灰阶 8–10 档，主色 5–10 档，预先定义，不现场 `lighten/darken`（§5.2 §5.3）。
- **不要在彩色背景上用灰色文字**：要的是降对比，不是去饱和，手挑同色相颜色（§2.3）。
- 亮度远离 50% 时提高饱和度，否则发灰（§5.4）；调整亮度可旋转色相，但**不超过 20–30°**（§5.4.2）。
- 对比度：正文 **4.5:1**，大字 **3:1**（§5.6）。
- **不能只靠颜色传达信息**，必须配图标/文字/形状（§5.7）。

### 12.5 深度（Depth）

- 光从上方来：凸起 = 上边缘更亮 + 下方小阴影；凹陷反之（§6.1）。
- 阴影表达高度，不是重要性（§6.2）；5 档足够（§6.2.1）。
- 完整阴影由两部分组成：大而柔的投射阴影 + 紧而深的接触阴影（§6.3）。

### 12.6 图像（Images）

- 不给位图放大：图标放大要**原尺寸包在更大的底形里**（§7.3.1）。
- 不缩小截图：改截更小的视口或局部（§7.3.2）。
- 用户上传图统一容器 + `cover` 裁剪，用内阴影或半透明内边框防“背景融合”（§7.4）。

### 12.7 收尾（Finishing Touches）

- 先强化默认元素，而不是加新元素：图标做列表符号、引号放大、自定义勾选框（§8.1）。
- 用强调色条提神：卡片顶部、激活导航、提示侧边（§8.2）。
- 背景降噪：低对比图案或形状（§8.3）。
- **空状态必须和功能一起设计**：配图/插画 + 强化 CTA + **隐藏此刻无用的 tabs、筛选**（§8.4）。
- 少用边框：阴影、色差、留白优先（§8.5）。
- 不被默认组件形态限制：下拉可分栏、表格可合并列（§8.6）。

### 12.8 液态玻璃与半透明材质

- 将玻璃作为**有边界的表面层**使用，而不是给所有容器统一添加模糊。先建立背景氛围，再安排主要玻璃面板、控件和焦点层级；各层通过间距、亮度、边缘与阴影表达关系。
- 固定并复用材质令牌：半透明填色、边缘线、高光、阴影和背景模糊强度。浅色与深色主题分别定义这些令牌，避免在组件中散落不一致的白色透明度与阴影值。
- 文字和重要图形的对比度必须按**实际叠加后的背景**验收。背景图案或渐变变化时，仍须维持文字、控件边界与焦点指示的可辨识度；不能仅凭设计稿中的单一取色判断。
- 对不支持 `backdrop-filter` 的环境提供不透明度更高的纯色回退。即使完全关闭模糊，面板仍要有清晰边界、可读文字和正确层级。
- 优先使用浅边缘、内高光与少量环境阴影塑造玻璃厚度；避免模糊叠加过重、卡片彼此融为一片或底层装饰穿透干扰文字。半透明效果不承担语义或状态的唯一表达责任。
- 在浅色/深色主题、窄屏、200% 缩放、键盘焦点和 `prefers-reduced-motion: reduce` 下分别走查。减少动态效果时，取消非必要入场和持续装饰动画；不为追求材质效果而持续动画化模糊或大面积背景。

## 15. 落地建议

1. **先改一处，建立基线**
   从产品中挑**最高频的一张表单**（如收货地址）或**流失最高的空态页**，只改一条（整段粘贴 + 智能默认），两周内对照前后数据。
   *收益*：验证“减少输入”是否真能提升完成率；*边界*：仅限前端交互可解的范围，解析能力需后端支持时另立需求。

2. **建立可用性度量口径**
   表单：完成率、字段纠错次数、平均填写时长；空态：空态页跳转率、搜索零结果率；报错：二次提交成功率；帮助：同类咨询量、帮助搜索点击率。
   *收益*：把“感觉不好用”变成可归因的指标；*边界*：需先补齐字段级埋点。

3. **把帮助变成需求入口**
   每月统计帮助中心 Top 10 问题，与产品迭代排期挂钩；文档只做兜底，能改界面就改界面。
   *收益*：从“越写越多的文档”转向“越来越少的问题”；*边界*：需打通客服/帮助中心数据。

## 16. 认知科学依据（理论 → 规范映射）

> 本章把规范背后的实证依据列出，每条含关键数值与出处，供评审时追溯「为什么这么定」。条目编号 `T1–T22` 可被正文引用。

### 16.1 注意与感知

| # | 理论（出处） | 关键结论与数值 | 落地规范 | 映射 |
| --- | --- | --- | --- | --- |
| T1 | 特征整合理论与视觉搜索（Treisman & Gelade 1980） | 颜色/形状等基本特征被并行、预注意加工；「特征捆绑」需要注意资源。独特征目标＝并行搜索（快）；特征组合目标＝逐项串行搜索（慢） | 目标元素靠**单一独特征**（一种颜色/徽标/形状）可辨，不让用户核对多特征组合；状态用色块 + 图标双编码 | H6、§12.4 |
| T2 | 格式塔分组 + Palmer 共同区域/连接（Wertheimer 等；Palmer 1992） | 邻近、相似、连续、闭合、共同命运是分组线索；共同区域（色块围合）与连接是分组强度最高的两种 | 分组优先用背景色块/边框围合或连接线，其次留白；组间距 > 组内间距（§3.6） | H4、§12.2 |
| T3 | 突现注意捕获（Theeuwes 等，onset capture） | 新出现的物体**自动且不自主地**捕获注意，与用户意愿无关 | 红点、toast、弹窗、入场动画是注意资源劫持，只用于真正需立即处理的事；同屏突现元素 ≤ 1 | H1、H8 |
| T4 | 变化盲视（Simons & Levin 1997 等） | 即使大幅变化，只要伴随掩蔽（转场、闪烁、遮盖）就常察觉不到 | 重要状态变化（价格、库存、身份、权限）禁止静默替换；保留位置 + 高亮/动画标记变化点 | H1 |
| T5 | F 形扫视与横幅盲区（Nielsen 2006；Benway & Lane 1998） | 阅读扫视轨迹呈 F 形，右侧与底部几乎不看；用户学会跳过长得像广告的位置 | 关键内容不放「广告位」（顶部通栏、右侧栏、通栏底条）；首屏左上优先承载最重要信息 | H8、§12.1 |

### 16.2 记忆与认知负荷

| # | 理论（出处） | 关键结论与数值 | 落地规范 | 映射 |
| --- | --- | --- | --- | --- |
| T6 | 工作记忆容量（Miller 1956：7±2；Cowan 2001：4±1，现代共识） | 即时可保持的信息块约 **4 个** | 单屏新信息块 ≤ 4；多步流程拆步，每步只依赖上一页 1–2 件事；选项分组每组 ≤ 4 项 | H6、§6.1 |
| T7 | 认知负荷理论（Sweller 1988） | 总负荷 = 内在（任务）+ 外在（呈现）+ 相关（建构）；设计只压**外在**负荷 | 删装饰、藏高级项、给默认值、用熟悉模式；示例优于抽象描述 | H5、H8、§12 |

<a id="sec-17"></a>

## 17. 无障碍与包容性设计

> 目标基线为 WCAG 2.2 AA；若适用法律、平台规范或合同要求更严格，应采用更严格的要求。本章的关键检查不等于整站合规认证。

### 17.1 结构与辅助技术

- 使用与内容和行为匹配的原生语义；标题层级连续，区域有可理解的名称，不以视觉样式替代语义。
- 每个输入均有可持久识别的标签；占位符不能作为唯一标签。图标按钮、图像链接和自定义控件提供明确的可访问名称。
- 禁用、选中、展开、校验结果和异步更新不仅改变颜色，还要通过语义属性或合适的状态播报传递。
- 键盘焦点始终可见、顺序合理且不被粘性栏或弹层遮挡；弹窗关闭后焦点返回触发点。
- 核心功能可仅用键盘完成，用户能按标准方式进入、操作并离开复合控件。

### 17.2 对比度、缩放与目标尺寸

| 检查项 | 验收基线 |
| --- | --- |
| 正文文字对比度 | 至少 4.5:1；大号文字至少 3:1 |
| 控件边界与有意义的图形 | 对理解或操作必要的视觉信息通常至少 3:1 |
| 半透明表面 | 以实际组合背景检查文字、焦点与控件边界；背景发生变化时仍需达到相应对比度基线 |
| 颜色编码 | 颜色之外还要有文字、图标、形状或位置等信号 |
| 文本放大 | 放大到 200% 时，文字和功能仍可使用，不被裁切或重叠 |
| 窄视口重排 | 约 320 CSS px 宽度下，普通阅读内容不要求整页双向滚动；二维数据表等应限制在局部容器 |
| 指针目标 | 遵循 WCAG 2.2 AA 最小目标尺寸要求及其例外；设计上常用触控目标优先按约 44×44 CSS px 预留区域 |

### 17.3 表单与错误

- 标签、输入说明和错误消息在程序结构上与字段关联；必填、格式和范围规则在输入前或输入时说明。
- 验证失败后把焦点或摘要引导到可操作的位置；修正后清除过时错误。
- 对拖动手势、限时操作和复杂身份校验提供可行的替代方式。
- 将自动扫描、键盘人工检查和选定辅助技术走查结合使用，不以单一设备的结果代表所有用户。

### 17.4 自查项

- [ ] 关键页面能否只用键盘操作，焦点是否可见且不被遮挡？
- [ ] 控件、图标按钮、错误与异步状态是否具有可被辅助技术识别的名称和状态？
- [ ] 文字、控件和必要图形的对比度是否达标？
- [ ] 200% 缩放与窄屏下是否仍可完成核心任务？
- [ ] 是否存在只靠颜色、声音、拖动或动画才能理解或完成的步骤？

## 18. 响应式布局与多种输入方式

### 18.1 视口覆盖

- 断点应由内容何时拥挤或失去可读性决定，不应机械地把某一设备型号等同于唯一断点。
- 按用户覆盖至少一个窄屏、一个中等宽度、一个桌面宽度；默认检查 320、375、768、1024 和 1280 CSS px，必要时补充横屏与更宽视口。
- 窄屏下优先重排信息、折叠次要内容或转换布局；不能通过缩小正文或压缩点击区域容纳桌面布局。
- 横向滚动仅用于确有二维结构需要的区域；页面整体不应出现意外横向溢出。

### 18.2 输入方式等价

- 关键操作同时考虑键盘、触控、鼠标和辅助技术；悬停才能出现的操作必须有焦点或触控替代入口。
- 不把拖动作为唯一方式；排序、滑块和画布等场景提供按钮、数值输入或其他替代方案。
- 触控目标留出足够间距；固定底栏与虚拟键盘不得遮住当前字段和主要操作。
- 测试慢网络、加载中断、离线和重新联网状态；重要操作须明确是否已提交，避免重复执行。

### 18.3 自查项

- [ ] 不同视口下信息层级、主操作和阅读顺序是否清晰？
- [ ] 页面是否有非预期的整页横向滚动、截断或遮挡？
- [ ] 悬停、拖动和复杂手势是否提供等价替代操作？
- [ ] 虚拟键盘、固定定位元素和缩放是否影响可操作区域？

## 19. 交互状态、文案与信任

### 19.1 核心组件状态

对核心组件按实际情况列出适用状态，不要求每个组件机械地具备全部状态。

| 状态 | 必须让用户知道什么 |
| --- | --- |
| 默认 / 可操作 | 当前可做什么，主要操作是什么 |
| 悬停 / 焦点 / 按下 | 指向哪个元素，键盘焦点在哪里 |
| 加载 / 提交中 | 操作已收到、是否可重复触发、如何继续 |
| 成功 | 结果是否保存、下一步是什么 |
| 校验失败 / 系统失败 | 哪里出错、原因或限制、如何修正 |
| 空态 / 无搜索结果 | 为什么没有内容、如何创建或调整条件 |
| 禁用 / 无权限 | 为什么不可操作、是否有替代路径 |
| 离线 / 超时 | 已完成与未完成的部分、重试是否安全、数据是否保留 |

### 19.2 反馈、动作风险与隐私

- 点击后及时反馈已收到操作。支付、创建订单等不可盲目重复的动作应显示处理中状态，并具备重复提交保护。
- 错误文案按“发生了什么 + 位置 + 原因 + 下一步”组织；需要用户行动的错误持续可见。纯成功提示可短暂显示，但不能作为唯一保存确认。
- 可逆动作优先提供撤销；不可恢复或高影响操作应在确认前说明影响对象、后果和恢复可能性。
- 默认值要基于可解释的上下文或明确规则，保持可见并易于修改；涉及金钱、隐私、公开发布和不可逆授权时，不代替用户作高风险决定。
- 日期、时间、数字、货币、姓名长度和文本方向适配目标地区；布局容纳翻译后的长文本。尊重减少动态效果偏好，避免闪烁或将运动作为唯一状态信号。
- 对液态玻璃等装饰材质，避免持续动画化大面积背景或模糊；动态效果应服务于状态变化，并在减少动态效果偏好下有明确回退。

### 19.3 自查项

- [ ] 核心组件适用状态是否都定义、渲染并验收？
- [ ] 提交反馈能否区分已收到、处理中、成功和失败？
- [ ] 高风险默认值、隐私选择和不可逆操作是否让用户充分知情？
- [ ] 动态效果、长文案与地区格式是否经过实际场景验证？

## 20. 可用性研究与量化验收

### 20.1 测试设计

- 每轮测试写清假设、目标用户、核心任务、成功定义和基线；任务描述使用用户的目标，不直接告诉测试者点击哪个按钮。
- 招募与真实使用场景相符的人群；面向有无障碍需求的产品，应让相关用户参与。探索性测试适合发现问题，不应直接当作总体人群统计证明。
- 结合观察式任务测试、客服反馈、搜索日志、埋点和问卷；A/B 测试可比较方案，但不能替代对原因和无障碍障碍的调查。
- 优先验证高风险、低成功率和高频任务。记录证据、严重度、负责人、修复建议和复验结果。

### 20.2 指标口径

| 指标 | 建议定义 | 使用注意 |
| --- | --- | --- |
| 任务成功率 | 满足预先定义成功条件的任务数 / 有效任务总数 | 另记部分成功与求助完成 |
| 完成时长 | 从任务开始到满足成功条件的时间 | 报告中位数及分布，说明超时处理 |
| 错误与恢复率 | 记录任务出错比例；恢复率为最终成功恢复的错误数 / 可恢复错误总数 | 区分用户误操作与系统错误 |
| 放弃率 | 未成功完成而离开的任务数 / 已开始任务总数 | 结合路径和访谈，不单独推断原因 |
| 搜索零结果率 | 零结果有效查询数 / 有效查询总数 | 明确空查询、机器人流量和隐私处理规则 |
| 无障碍阻断数 | 阻止目标用户完成关键任务的问题数 | 记录影响范围、辅助技术和复现步骤 |

### 20.3 发布验收

- P0 问题必须在发布前解决或由有权负责人明确记录风险处置；关键路径无法通过键盘完成、重要内容不可读或发生严重数据丢失时不得以视觉打磨抵消。
- P1 问题有明确负责人和修复计划；P2 问题进入可追踪的改进队列。
- 对照同口径基线比较改动前后结果，记录样本、时间范围、版本与数据限制，并检查是否让某类用户、设备或辅助技术体验变差。
- 每次修复后按原复现路径复验，并回归相关核心任务及受影响的响应式、键盘和辅助技术路径。

### 20.4 自查项

- [ ] 高优先级问题是否有证据、严重度和可验证的修复条件？
- [ ] 指标的分母、事件边界、排除项和采集隐私是否明确？
- [ ] 是否使用真实用户或合理代表样本验证关键流程？
- [ ] 修复后是否按相同任务和指标复验，并检查回归影响？

## 21. 务实走查清单 · 六大模块

> 一份可直接用于设计评审、代码自查与用户走查的**务实清单**。按六大模块组织，每条附「自检问题 + 反例 → 改法 + 落地清单」。与前面以尼尔森原则 / Refactoring UI 为主的理论章节互补：本章偏「拿到一屏就能逐条过」的实战。
> 用法：设计或评审时**逐屏**过一遍六个模块的自检问题；上线前用文末「验收清单」做一轮走查，并用「返回行为专项」验证导航健壮性。

### 21.1 总览：六大模块

| 模块 | 关注对象 | 对应理论 |
| --- | --- | --- |
| **报错模块** | 出错时用户能否看懂、定位、继续 | 关联 H9 错误恢复 |
| **美观简约** | 每一屏的信息优先级与视觉层次 | H8 美学极简 |
| **组块** | 信息如何分块、命名、对齐用户心智 | 组块（Chunking）/ 接近律 |
| **峰终定律** | 流程中最长 / 最痛的一段与最后一屏 | Peak-End Rule（Kahneman） |
| **泰斯勒定律** | 最常走的一段流程与复杂度分配 | Tesler's Law of Conservation of Complexity |
| **即时反馈** | 每次操作的响应节奏 | NN/g 十大可用性原则 #1「系统状态可见」 |

### 21.2 报错模块

**自检问题**
- 用户看得懂吗？——能说出是哪件事（如「第 3 张图太大了」），而不只是「操作失败」。
- 知道错在哪吗？——给出具体位置（如「发布失败（4012）」「结算页：下单」「确认页」）。
- 知道下一步点哪吗？——给一个明确按钮（如「压缩这张，再发布」）。

**反例 → 改法**
- 只说「失败」 → **原样留着，只改出错的那一处**；不要一失败就清空已填内容。
- 屏幕中间闪两秒 → **贴在出错的那一处，框出来**（行内 / 字段级报错，而非全局 toast）。
- 一失败就清空 → 保留用户刚填的内容，仅标注并高亮错误项。
- 自己发明分法 → **卡面怎么印就怎么分**；或让用户自己打空格；输入时边打边自动加空格。
- 分法和他手里那份不一样 → 对齐用户已有的实物 / 习惯分法，降低「对到一半丢了位置」的挫败。

**落地清单**
- [ ] 报错文案说人话、点名具体事项
- [ ] 错误定位到具体字段 / 区块并高亮
- [ ] 提供明确的下一步动作（按钮 / 链接）
- [ ] 出错不清空已填内容，仅标注错误
- [ ] 输入分法与用户既有习惯一致

### 21.3 美观简约

**自检问题**
- 每样都问：这一步用得上吗？
- 用不上 → 拿掉，或往后放。
- 用得上 → 越重要，越大、越靠前。
- 八行一样大、一样灰 → 分块、块间留白、每块一个小标题。

**反例 → 改法**
- 八行一样大一样灰 → **分块 / 块间留白 / 每块一个小标题**，建立视觉层次。
- 弹窗按钮含糊 → 用一两个词写出**点了会怎样**（写动作，如「删除」而非「确定」）。
- 两个按钮会读拧 → **两边都写清动作**。
- 标题没说清后果 → 标题点明「问哪件事、会怎样」（如「删除后不可恢复」）。

**落地清单**
- [ ] 非必要元素移除或后置
- [ ] 重要操作视觉权重更高（尺寸 / 位置）
- [ ] 同屏内容分区并命名
- [ ] 按钮文案即动作，双按钮不歧义
- [ ] 危险操作标题说明后果

### 21.4 组块（Chunking）

**自检问题**
- 这一屏分成了几块，每块有名字吗？
- 用户要拿它跟别处对一遍吗？——要对就分组。
- 对到一半丢了位置 → 分组 + 实时辅助（边打边加空格）。

**反例 → 改法**
- 一长串连着 → **分块 / 块间留白 / 每块小标题**。
- 金额难读 → 金额加逗号、写上「万」等单位。
- 自己发明分法 → **卡面怎么印就怎么分**；或让用户自己打空格。

**落地清单**
- [ ] 长内容切分为有命名的小块
- [ ] 块间留白区分层次
- [ ] 需对照的内容分组呈现
- [ ] 数字 / 金额按阅读习惯格式化

### 21.5 峰终定律（Peak-End Rule）

**自检问题**
- 重点关注：产品里**最长的那串**，或**信息最多的那一页**。
- 这一段里，用户最难受的是哪一下？
- 最后一屏，告诉他**结果和接下来会怎样**了吗？
- 最后一屏，有没有在向他要东西？→ 拿掉，这一屏只交代结果。

**反例 → 改法**
- 「提交成功」一闪而过 → **停在结果页**：结果、金额、什么时候、下一步，逐一交代。
- 刚办完就弹打分、开会员、分享 → **拿掉**，这一屏只交代结果。
- 替他填了但没法核对 → 让他能**一眼核、一下改**；只有他知道的，留给他。

**落地清单**
- [ ] 长流程 / 信息密集页重点打磨
- [ ] 结果页交代结果 + 时间 + 下一步
- [ ] 完成页不强行索取（打分 / 会员 / 分享）
- [ ] 预填内容用户可核可改，隐私信息留白

### 21.6 泰斯勒定律（Tesler's Law）

**自检问题**
- 重点关注：产品里**最常走的一段流程**。
- 这一段里，用户最难受的是哪一下？
- 自动识别：用户手里现成的，能认出来吗？
- 智能默认：这一栏，能给个靠谱的默认吗？
- 自动补全：要打字的栏，能边打边补全吗？

**反例 → 改法**
- 弹窗连拦两次 → **先修它：拿掉拦路的弹窗**（如「继续退款」是灰色小字却拦路）。
- 要挽留 → 页面上留一行**不挡路**的提示即可。
- 一长串让他一段段抄 → **整段粘进来，系统拆开填好**。
- 每次从空白开始选 → **先选好最可能的，错了一点就改**（智能默认）。

**落地清单**
- [ ] 高频流程识别并减负
- [ ] 移除不必要的拦截弹窗
- [ ] 支持整段粘贴自动拆分
- [ ] 提供合理智能默认
- [ ] 输入项支持自动补全 / 识别

### 21.7 即时反馈（Immediate Feedback）

**对应理论**：NN/g「十大可用性原则」第 1 条「系统状态可见」。

**时间阈值（响应节奏）**
- 0.1 秒内 → 像在直接操作（即时）。
- 超过 1 秒 → 先说「计算中」。
- 超过 10 秒 → 给进度，也给个取消。
- 回应别过头：每点一下就整页刷新，就成了噪音。

**表单 / 筛选面板场景（同一块筛选面板，改四处）**
1. 选项旁边标上能筛到几件，是零的直接灰掉。
2. 点下去马上有回音：这一行、顶上的「已选」、按钮上的数**一起变**。
3. 选过的条件摆在顶上，点 × 就能删。
4. 按钮别只写「确定」，写上会看到几件。

**其它**
- 「继续退款」是灰色小字却连拦两次 → 先修拦路弹窗。
- 能自动识别 / 智能默认 / 自动补全的，不要让用户手填。

**落地清单**
- [ ] 操作在感知阈值内给回应
- [ ] 长任务有状态文案 / 进度 / 取消
- [ ] 避免无意义的整页刷新
- [ ] 选项实时显示结果数量
- [ ] 选中态多处联动可见
- [ ] 条件可一键清除

### 21.8 验收清单（走查用）

**通用逐条过**
- [ ] 用户看得懂吗？说出是哪件事
- [ ] 知道错在哪吗？贴在出错的那一处框出来
- [ ] 知道下一步点哪吗？给个按钮
- [ ] 用不上→拿掉 / 往后放；用得上→越大越靠前
- [ ] 这一屏分成了几块，每块有名字吗？分块、块间留白、每块小标题
- [ ] 用户要拿它跟别处对一遍吗？要对就分组
- [ ] 最后一屏，告诉他结果和接下来会怎样了吗？
- [ ] 最后一屏，有没有在向他要东西？拿掉，只交代结果
- [ ] 弹窗按钮写动作；两个按钮都写；标题说清后果
- [ ] 自动识别 / 智能默认 / 自动补全到位
- [ ] 报错不清空已填内容，仅标注错误

**返回行为专项（导航健壮性）**

按返回时，应满足：
- **列表回到原位**：滑到第 20 条，点进去再返回，还在那一行 → 留住列表。
- **大图 / 弹窗只关它自己**：打开大图按返回，只关大图 → 先关上层。
- **分步表单只退一步，内容还在**：分步表单走到第 2 步按返回，退一步、字还在 → 一步一退。

> **验证方法**：照这张卡做一遍，告诉我每次落在哪儿、丢了什么。重点检查：列表回到原位；大图、弹窗只关它自己；分步表单只退一步、内容还在。

### 21.9 用法建议

1. **设计阶段**：画完一屏，逐模块过自检问题，把反例改成改法。
2. **评审阶段**：用「验收清单」逐条打勾，未过项列入整改。
3. **测试阶段**：专人按「返回行为专项」走查导航；用「照这张卡做一遍」的方法记录每一步的落点与丢失。
4. **复盘**：把高频痛点回流到对应模块，持续收敛复杂度（泰斯勒定律）。

## 22. 表单校验与防错（输入防错四法）

> 对应原则：H5 错误预防、H9 识别诊断并从错误中恢复。核心心法：**能在上一行挡住的，别留给下一行**——把错误拦截在它发生的地方，而不是攒到提交时一起报。
> 四道防线按「拦截时机从早到晚」排列；前三道尽量让用户**根本犯不了错**，最后一道只兜底真正漏网的。

### 22.1 总览：四道防线与三个坑

**四道防线**
1. **让它选不上（防手滑）**：不合规则的选项直接置灰、点不到。
2. **替人改过来（防手滑）**：接受空格、弹对键盘、自动规整。
3. **按下前摆出来（防想错）**：约束在按下前就看得见。
4. **最后才报错漏网的（贴着那一项，填完再说）**：只兜底漏网的，且报错贴着那一项。

**三个坑**
- **别挡过头**：把对的也挡在外面（卡太死，合法的也进不来）。
- **灰着不说原因**：用户只知道点不了，不知道为什么。
- **报得太早**：字还没打完就报错。

### 22.2 第一道：让它选不上（防手滑）

- **规则**：不合规则的选项直接置灰、点不到，让错的组合从根源选不出来。
- **示例**：退房日期早于 / 等于入住日时一律置灰；过去、满房、可订日期用不同视觉区分，不能「全灰一片」。

**落地清单**
- [ ] 非法组合在源头就不可选（如退房 < 入住）
- [ ] 禁用项有视觉区分，不是「全灰一片」
- [ ] 禁用原因可探知（悬停 / 图例说明「满房」「已过」）

### 22.3 第二道：替人改过来（防手滑）

- **规则**：别让用户手动对齐格式，系统替他规整；并给对的交互（键盘、空格）。
- **示例**：手机号弹数字键盘、输入自动去空格；用户填 `138 0013 8000`，系统存为 `13800138000`，不打回重填。

**落地清单**
- [ ] 输入自动去空格 / 规整，不强制用户按格式
- [ ] 移动端弹对应键盘（tel / email / number）
- [ ] 明显格式错误时就地规整，而非清空重来

### 22.4 第三道：按下前摆出来（防想错）

- **规则**：约束在按下前就摆在明处，让用户按前看得出选错。
- **示例**：日期「晚数」摆在按钮旁好对一下（「入住 3 晚 → 退房」）；预期结果预览在提交按钮附近。

**落地清单**
- [ ] 关键约束在操作时可见（非藏进帮助）
- [ ] 选择结果有即时预览（晚数、总价、范围）
- [ ] 破坏性 / 不可逆操作的后果在按下前点明

### 22.5 第四道：最后才报错漏网的（贴着那一项，填完再说）

- **规则**：只兜底真正漏网的；报错贴着那一项、填完（离开该项）再说，不堆页顶。
- **示例**：订房页三处错误各贴各行——① 第 1 行，② 第 2 行，③ 第 3 行。
- 与第 21 章「报错模块」（§21.2）呼应：报错同样要求贴着出错处、说人话、给下一步。

**落地清单**
- [ ] 报错定位到具体字段，就地高亮，不堆顶部
- [ ] 校验时机为「离开该项且仍错」再提示（非每次按键）
- [ ] 提示说清「还差几位 / 什么格式」，而非只说「格式错误」

### 22.6 三个坑

> 每条先给「规则」，再给「示例」，便于评审时区分原则与反例。

**坑一 · 别挡过头（别把对的也挡在外面）**
- **规则**：校验不能卡太死，合法的输入也要能进得来。
- **示例**：海外号码位数和国内不一样，若手机号只认 11 位就进不来；应给「不限格式的框」（如写「请输入手机号」而非「请输入 11 位手机号」），或放宽长度与区号。

**坑二 · 灰着不说原因**
- **规则**：禁用项不能只灰着，要让用户知道为什么点不了。
- **示例**：过去日期和满房若一样灰，人只知道点不了、不知道为什么；应做区分——满房标「满」、过期标「已过」。

**坑三 · 报得太早**
- **规则**：校验不要输入中打断，等离开该项、还不对再提示。
- **示例**：手机号还没打完（`+86138|`）就弹「手机号格式错误」太早；应等用户离开该项且仍不对，再提示「还差几位」。

### 22.7 自检（逐条过）
- [ ] 能在上一行挡住的，没留给下一行
- [ ] 非法组合源头不可选，禁用项有区分与原因
- [ ] 输入自动规整、弹对键盘，不逼用户按格式
- [ ] 约束在按下前可见，关键结果有预览
- [ ] 漏网的报错贴着字段、离开该项才提示、说清还差什么
- [ ] 没把合法输入误挡（海外 / 特殊格式有出口）
- [ ] 报错不堆页顶、不输入中打断

## 23. 占位文字（Placeholder）的正确用法

> 对应原则：H6 识别而非回忆、H1 系统状态可见。核心矛盾：**占位文字（框内灰字）在用户开始填写后就会消失**——若它承载了「这是填什么的 / 有什么要求」这类关键信息，填写中与填写后就再也看不到了。占位文字只能做补充，不能当唯一说明。

### 23.1 三条规则

**规则一 · 填满还认得出吗？→ 框上加标题**
- **规则**：每个输入框都应有**始终可见的标题（label）**，不依赖占位文字表明「这是填什么的」。
- **示例**：填满后占位灰字消失；若只有灰字、没有标题，用户回头看就不知道这一格是手机号还是邮箱。把标题放在框上方 / 左侧，填不填都在。

**规则二 · 打字时要求还在吗？→ 写到框下**
- **规则**：格式、范围等要求写在**框下方常驻提示（hint）**，而不是只放在占位文字里——占位文字在聚焦输入时会消失。
- **示例**：「请输入 11 位手机号」若只在占位里，用户一打字它就没了；改放到框下方，打字时仍可见。

**规则三 · 灰字是说明还是例子？→ 留空或写「例如」**
- **规则**：占位灰字要让人分清是「说明」还是「例子」。纯说明就写清要求；若给的是样例值，明确加「例如」前缀，避免被当成要照抄的格式。
- **示例**：占位写「张三」易被误认为要填这个名字；改为「例如：张三」或「请输入姓名」，区分说明与示例。

### 23.2 验收方法（走查占位文字）

> **假设每一格都已经填好，框里的灰字全都消失了。** 请告诉我：哪几格看不出是填什么的、要求是什么？凡有此情况的，就需要改（补标题 / 把要求移到框下 / 区分说明与示例）。

**落地清单**
- [ ] 每个输入框都有始终可见的标题（不靠占位文字表明用途）
- [ ] 格式 / 范围要求写在框下常驻提示，输入时仍可见
- [ ] 占位灰字分清说明与示例（示例加「例如」或留空写清要求）
- [ ] 填满后仍能辨认每格的用途与要求（灰字消失不影响理解）
